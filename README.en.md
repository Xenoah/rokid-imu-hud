# IMU HUD for Rokid Glasses — 0.1.4-preview

[日本語](README.md) | [Download APK and source](https://github.com/Xenoah/rokid-imu-hud/releases/tag/v0.1.4-preview)

An independent Android HUD combining an artificial horizon with a two-axis G meter. Designed for Snapdragon AR1 Rokid Glasses running YodaOS-Sprite. Runtime IMU acquisition, fusion, acceleration processing, drawing and controls stay on the glasses. No smartphone, Bluetooth connection, external sensor, account or server is required during normal use.

## This version

**Recover from unstable OS attitude**

Keeps the raw-IMU statistics window when only OS attitude changes. Rejects unstable OS attitude and switches to accelerometer/gyroscope fusion on the glasses.

This revision has not been tested on physical hardware. There is still no calibration deadline when larger movements persist.

## Features

- Fixed aircraft marker, moving horizon, 10° pitch ladder, roll scale and numeric pitch/roll.
- ±2G circular meter with 0.5G rings, short trail, LAT/LONG values and filtered planar peak hold.
- Combined, horizon-only and G-meter-only modes.
- Green line art on black/non-emitting background; 480×400 logical HUD fitted into the available surface.
- Separate sensor, vsync drawing and optional CSV threads. Requests 200Hz IMU input and targets 60fps; actual rates depend on firmware and hardware.
- Recenter resets attitude/G reference, peak and display filters. It does not estimate physical position.

## Install and launch

Download `RokidHUD-0.1.4-debug.apk` from this version's release assets. Android 12/API 31 or later is required. The package is `dev.xenoah.rokidhud`.

Enable ADB using the official Rokid setup procedure and a data-capable development cable. A charging-only cable may not work. A PC or phone may be used for initial setup, but is not needed by the running app.

```sh
adb devices
adb install -r RokidHUD-0.1.4-debug.apk
adb shell am start -n dev.xenoah.rokidhud/dev.xenoah.hud.MainActivity
```

The distributed APKs share the original debug signing certificate. Your own local build normally uses another key and cannot update these APKs in place. Do not uninstall automatically: uninstalling removes app data. Normal launch uses the device app list when supported by its firmware.

## Controls

| Glasses input | Action |
| --- | --- |
| Two-finger double tap on the right touch panel | Recenter / recalibrate |
| Single-finger single tap (`KEYCODE_ENTER` up) | Cycle display mode |
| Single-finger double tap (`KEYCODE_BACK`) | Normal system back / exit |
| Reserved function/AI long presses | System behavior is preserved |

Recenter receives the documented `com.android.action.ACTION_TWO_FINGER_DOUBLE_TAP` event while the activity is foregrounded and the glasses are worn. It does not abort the broadcast. Delivery and coexistence on each firmware still require device testing.

## Calibration

Normal startup gathers about one second of stationary input. It may keep waiting while movement is detected; see the version-specific limitations above.

Startup displays CALIBRATING / KEEP HEAD STILL, followed by READY. Recenter displays RECENTERED for about one second when complete. Standard calibration estimates gyro bias, limited accelerometer bias and an initial attitude. Recenter sets pitch/roll to zero and clears G filters and the peak. A single static pose cannot identify every accelerometer scale/bias error. Six-axis IMU data cannot perfectly distinguish constant yaw rotation from gyro bias or sustained linear acceleration from gravity.

## Sensors, axes and fusion

This uses Android `SensorManager`, `SensorEventListener`, `SurfaceView`/`Canvas`, `Choreographer`, hardware key events and the documented Rokid broadcast. It follows the current glasses bare-metal Android route, with no CXR-S phone dependency and no old Rokid Max/Station SDK. Sources and remaining uncertainties are in [official-research.md](docs/official-research.md).

Attitude preference: `TYPE_GAME_ROTATION_VECTOR`, then `TYPE_ROTATION_VECTOR`, then local gyro/accelerometer Mahony fusion. Invalid or stale input is rejected. Accelerometer values include gravity; the engine removes it using attitude, transforms the residual through the inverse recenter quaternion, then applies the G-meter low-pass filter. One G is exactly 9.80665m/s².

Documented device axes: +X right, +Y up, +Z toward the wearer. LAT positive is acceleration to the right. LONG positive is forward, corresponding to −Z in the neutral reference. The dot follows acceleration, not apparent inertial force. The production axis map transforms accelerometer, gyroscope and quaternion consistently. Confirm physical signs using the [device acceptance checklist](docs/device-acceptance.md) before changing the map.

The default G cutoff is 4Hz and attitude-display smoothing is 12ms. Tuning constants are in `Config.java`. Sensor processing and display rates are separate. Detailed equations and conventions: [coordinates-and-fusion.md](docs/coordinates-and-fusion.md).

## Display size

The app uses a 480×400 logical HUD. The official UI guide reviewed during development described a 480×640 physical display with a 480×480 recommended central area; on a 480×640 surface the logical HUD is centered at y=120. Check `adb shell wm size` and the startup log on your model. Black means non-emitting pixels on the glasses. This is a foreground application, not a system overlay or a world-anchored 6DoF display.

## Build

JDK 17, Android SDK Platform 35, Build Tools 35.0.0 and Platform Tools are required. The project pins AGP 8.9.2 and Gradle 8.11.1. Initial dependency downloads need networking; app runtime does not.

```sh
./gradlew :core:verify :app:assembleDebug :app:lintDebug
# Windows: .\gradlew.bat :core:verify :app:assembleDebug :app:lintDebug
# Direct SDK build without Gradle:
python3 tools/build-apk.py --sdk /path/to/android-sdk
```

Output: `app/build/outputs/apk/debug/app-debug.apk`. The provided APK was built directly using AOSP SDK tools, with API 36 compilation stubs and minSdk 31 / targetSdk 35. Direct compilation and static package inspection are not Android runtime testing or lint. See [build report](docs/apk-debug-report.md). GitHub Actions publishes the existing signed APK; it never substitutes a newly generated signing key.

## Diagnostics and verification

```sh
sh tools/test-core.sh
adb shell am force-stop dev.xenoah.rokidhud
adb shell am start -n dev.xenoah.rokidhud/dev.xenoah.hud.MainActivity --ez debug true
adb logcat -v threadtime RokidHUD:I '*:S'
python3 tools/debug-device.py --apk dist/RokidHUD-0.1.4-debug.apk
```

Use `--ez force_fusion true` at launch to exercise local sensor fusion. Optional CSV logging writes private `files/hud-debug.csv` at 10Hz, up to 36,000 rows; it is overwritten on the next debug launch. Log collection scripts are included. No microphone, camera, GPS, Internet or Bluetooth permission is requested.

The archived version records 39 synthetic IMU checks and 11 static APK checks. They cover simulated rest, right/left roll, up/down pitch, forward/back/lateral acceleration, recenter and drift-related cases. Actual device motion, touch delivery, optical latency and sustained frame rate are not certified by these tests. CPU draw/post time is not motion-to-photon latency.

## Limitations

- The meter measures acceleration of the glasses, including head movement and walking vibration. It is not a vehicle-mounted IMU.
- Six-axis fusion has yaw drift and cannot fully separate sustained acceleration from gravity. Yaw drift can rotate the saved horizontal G reference.
- Large pitch angles near ±90° make roll ambiguous; this HUD targets ordinary head poses.
- Sampling rate, 60fps, end-to-end latency and battery duration depend on the device and firmware and remain measurement targets.
- No absolute position, speed, altitude or double integration is implemented. This is not a certified flight, navigation or vehicle-control instrument.
